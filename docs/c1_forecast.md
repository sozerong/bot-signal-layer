## 2. 예측식

```
클라우드 시간 = (앱 안 고정 시간 685초) + 앱 63개 × (YARN 시작 추가 Y초)
             + (태스크 일 2,438 ÷ 실행 코어 4) × (코어 속도 비 k)
             + 앱 사이 145초 + 클러스터 만들기·지우기 C초 + BigQuery dbt D초
```

| 변수 | 낮게 | 중간 | 높게 | 근거 |
|---|---|---|---|---|
| 실행 코어 | 4 | 4 | 4 | 〔근거: 워커 2대 × 2 vCPU, 드라이버는 마스터 (engine_selection.md E7 예시 구성)〕 |
| Y (앱마다 YARN에서 executor 받는 추가 시간) | 10초 | 20초 | 30초 | 〔근거: 확인 필요(첫 클러스터에서 빈 앱 하나의 시작 시간을 잰다). 판단: 로컬 local 모드에는 이 단계가 없다〕 |
| k (e2 vCPU 하나 대 로컬 코어 하나의 느린 정도) | 1.0 | 1.5 | 2.0 | 〔근거: 확인 필요(같은 하루치 load_events의 태스크 시간 비교). 판단: e2는 공유 코어 계열이다(소스: [spendark e2-standard-2](https://spendark.com/instances/e2-standard-2/) "Burstable (shared vCPU)")〕 |
| C (클러스터 만들기 + 지우기) | 120초 | 180초 | 300초 | 〔근거: engine_selection.md E7 "클러스터를 만드는 데 몇 분 걸린다". 확인 필요(첫 생성 시간)〕 |
| D (BigQuery dbt build) | 60초 | 120초 | 180초 | 〔근거: 로컬 DuckDB 22초(M-17). 판단: 모델마다 BigQuery 쿼리 하나라 고정 지연이 붙는다. 확인 필요〕 |

**예측 결과**

| | 낮게 | 중간 | 높게 | 근거 |
|---|---|---|---|---|
| 앱 고정 몫 (685 + 63Y) | 1,315초 | 1,945초 | 2,575초 | 〔근거: 계산〕 |
| 태스크 일 몫 (610k) | 610초 | 915초 | 1,220초 | 〔근거: 계산: 2,438 ÷ 4 = 609.5〕 |
| 나머지 (145 + C + D) | 325초 | 445초 | 625초 | 〔근거: 계산〕 |
| **합** | **37.5분** | **55분** | **73.7분** | 〔근거: 계산〕 |
| 로컬 대비 | 2.2배 | 3.2배 | 4.2배 | 〔근거: 계산: ÷ 17.37분〕 |

- **예측의 핵심: 느려지는 이유의 절반 이상이 계산이 아니라 앱 63개의 고정 시간이다.** 중간값 기준 1,945 ÷ 3,305 = 59%다. 〔근거: 계산〕
- 그래서 처방 후보가 미리 보인다: 날마다 앱 하나가 아니라 태스크마다 앱 하나(7일을 한 앱 안에서 차례로)로 묶으면 앱이 63개에서 9개로 준다. 줄어드는 시간은 54 × (10.9 + Y)초, 즉 19 ~ 37분이다. 〔근거: 계산: 685 ÷ 63 = 10.9초. 판단: 날짜별 overwritePartitions와 쓰기 가드는 한 앱 안의 반복에서도 그대로 돈다(run_sql.py 75번째 줄은 쓰기 단위가 날짜 파티션)〕
- 로컬에서 잰 결과 (M-38): 앱 63 → 9개로 컨테이너 시간 1,072 → 586초. 아낀 앱 고정 시간은 앱당 10.9초가 아니라 6.1초였고, 대신 태스크 실행 합이 22% 줄었다. 위 "19 ~ 37분"은 앱당 고정 시간을 크게 잡은 값이라, 클라우드에서는 54 × (6.1 + Y)초로 고쳐 본다. 묶음은 결정 32로 기본이 되었다. 〔근거: 측정: M-38. 결정 32. 확인 필요(Y = YARN 앱 시작, C1 첫 실행)〕
- 묶을 때 잃는 것: 하루가 실패하면 그 태스크의 앱 전체를 다시 띄운다. 7일 중 어디서 멈췄는지는 날짜별 쓰기 기록(run_id)으로 남겨, 다시 돌릴 때 끝난 날짜를 건너뛴다. 〔근거: 판단: 멘토 "체크포인트를 걸고 왜 멈췄는지 추적"(mentoring_2026-11-19.md 29행). 코드: evidence 표의 run_id 컬럼(local_baseline.md 1절)〕
- 메모리 위험 (M-37로 고침): M-17의 6.09GiB는 필요량이 아니라 JVM이 받은 힙만큼 키운 꼭짓점(7일, 페이지 캐시 포함)이었다. 가장 큰 날 features_account의 태스크 최대 실행 메모리는 0.672GiB이고, 컨테이너 3g까지 spill 0, 2g에서도 실패 없이 spill 1.14GiB로 끝났다. 그래서 e2-standard-2(8GB)의 executor 하나로 충분하다고 본다. 머신 크기 예측은 e2-standard-2 그대로 두고, 더 줄일 근거로 쓴다. 〔근거: 측정: M-37 상한별 표, M-17. 결정 31. 소스: [e2-standard-2 8GB](https://www.devzero.io/instances/gcp/e2-standard-2). 확인 필요(첫 실행에서 Spark UI executor 최대 실행 메모리와 spill)〕

- 비교: 관리형 Airflow(Composer 3)는 외부 추정으로 최소 월 300달러 이상이라 크레딧 전부와 비슷하다. VM 방식이면 한 달 비용이 크레딧의 1% 안이다. 〔근거: gcp_research.md 6절 [36]. 계산: 2.5 ÷ 300 = 0.8%〕
- 무료 체험 CPU 8개 제한: 클러스터 6 + Airflow VM 2 = 8로 여유가 없다. 〔근거: engine_selection.md E8 남은 것〕
- 예산 알림만으로는 지출이 멈추지 않는다. 첫날 예산 알림과 결제 끊기 함수, 클러스터 유휴 자동 삭제를 건다. 〔근거: gcp_research.md 7절〕
