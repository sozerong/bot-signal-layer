# G1: raw json.gz를 다시 처리하는 비용

설계 문서 6.1절 G1. 관련 결정: D2(raw는 원본 그대로), D7(base 물리화).

## 1. 원한 장점 (A를 고른 이유)
raw를 json.gz 그대로 둔다(D2). 변환 버그가 나거나 원천 형식이 바뀌어도 원천에 다시 가지 않고 raw에서 다시 만들 수 있다.
원천은 다시 받을 수 없을 수도 있다(2026 수집량 붕괴).

## 2. 예상 문제 (실행 전에 내가 쓴다)
> 실행 전에 쓴다. 쓴 뒤에는 고치지 않는다. 틀린 예상도 기록이다.

- 한 달(720개 파일)을 다시 처리하면 몇 분이 걸릴까: parse 기준 단일 스레드로 **약 90분** (파일당 약 7초 × 720).
- 스레드를 1 → 4로 늘리면 몇 배 빨라질까: parse는 **1.2배 이하**. read는 **약 1.8배**.
- read 단계와 parse 단계 중 어디가 비쌀까, 몇 배: parse가 read의 **약 4배**.
- 이유
  - 120MB gz는 풀면 1GB 안팎일 것이다. 표준 json은 대략 100~300MB/s라서 파일당 4~8초가 걸린다. read(1.8초)보다 몇 배 비싸다.
  - json.loads는 GIL을 쥔 채로 돈다. 스레드를 늘려도 한 번에 하나만 파싱한다.
  - zlib 압축 해제는 C 안에서 GIL을 놓는다. 그래서 read는 어느 정도 병렬이 된다. 다만 줄 나누기는 Python에서 하므로 4배까지는 안 간다.

## 3. 실행
프로젝트 루트에서 실행한다. **다운로드가 끝난 뒤** 돌린다. 다운로드 중에는 네트워크와 디스크가 같이 바빠서 숫자가 흔들린다.
첫 실행은 버린다. 첫 실행은 디스크에서 읽고, 두 번째부터는 OS 캐시에서 읽는다. 이 차이 자체도 볼 만하다.

```
python experiments/g1_reparse/g1_reparse.py --workers 1 --stage read  --quiet
python experiments/g1_reparse/g1_reparse.py --workers 1 --stage parse --quiet
python experiments/g1_reparse/g1_reparse.py --workers 4 --stage read  --quiet
python experiments/g1_reparse/g1_reparse.py --workers 4 --stage parse --quiet
```

추천 표 (workers 1, 2, 4, 8 × stage read, parse)

2026-11-12 실행. 파일 8개(2025년 15일 12시 파일, 709MB, 173만 줄). 데워 두기 1회는 버렸다. D13 다운로드가 느리게(파일당 수 분) 같이 돌고 있었다.

### 내부를 보는 계기
- **작업 관리자 → 성능 → CPU → 그래프를 논리 프로세서로 변경**: 코어 16개 중 몇 개가 바쁜지 눈으로 본다.
- **py-spy record**: 시간이 어느 함수에서 쓰였는지 불꽃 그래프로 본다. 브라우저로 svg를 연다.
  ```
  py-spy record --nonblocking -o g1.svg -- python experiments/g1_reparse/g1_reparse.py --workers 4 --stage parse --quiet
  ```
  - 이 PC(Windows, Python 3.12.8)에서는 `--nonblocking`이 필수다. 이 옵션이 없으면 "Failed to suspend process"로 실패한다.
  - 대가: 멈추지 않고 읽어서 스택이 가끔 섞인다(`readline` 아래에 `JSONDecoder`가 붙는 식). 오류 샘플도 20~30% 나온다. 비율로만 본다.
  - `--gil`(GIL을 쥔 스택만 기록)은 이 조합에서 지원되지 않는다.
  - `--format raw --threads`로 뽑으면 스레드별로 집계할 수 있다. `--idle`을 붙이면 기다리던 샘플까지 들어간다.
- **py-spy top**: 실행 중에 함수별 시간을 실시간으로 본다(`py-spy top --nonblocking -- python ...`).
- 참고: 이 PC는 논리 코어가 16개다. 코어평균 1.00 = 코어 1개만 썼다는 뜻이다.

## 4. 실제로 본 것 (숫자)

**예상과 비교**
| 질문 | 예상 | 실제 |
|---|---|---|
| 한 달을 다시 처리하는 데 걸리는 시간 (parse, 단일 스레드) | 약 90분 | **약 58분** (2025 샘플 평균 89MB/파일, 4.8초/파일 × 720). 고를 달의 파일 크기에 따라 달라진다 |
| parse, 스레드 1 → 4 | 1.2배 이하 | **0.99배** (38.4 → 38.8초). 전혀 안 빨라졌다 |
| read, 스레드 1 → 4 | 약 1.8배 | **1.26배** (12.6 → 10.0초). 8개로 늘리면 오히려 1.18배다 |
| parse ÷ read | 약 4배 | **3.0배**. json만 떼면 25.8초로 read의 약 2배다 |

**예상 못 한 것**
1. **스레드를 늘리면 CPU만 더 쓴다.** parse에서 스레드를 1 → 4로 늘리면 걸린 시간은 그대로인데 CPU 시간은 37.6 → 48.0초로 28% 늘었다. 일은 그대로인데 CPU를 더 태운다.
2. **메모리는 문제가 아니다.** 어떤 조합에서도 27~31MB다. 한 줄씩 읽어서 파일 크기와 상관없다. 이 단계의 병목은 CPU다.

**내부 (py-spy, workers 4, parse, 파일 4개)**
- 4개 워커 샘플 중 실제로 일하던 비율은 32%다(7,200 중 2,328). 나머지 68%는 기다렸다. 일하던 워커는 순간마다 평균 1.3개로, 코어평균 1.24와 맞는다.
- 함수별 비율이 스레드 수에 따라 뒤집혔다.

  | | json | gzip/readline | 기타 |
  |---|---|---|---|
  | workers 1 | 64% | 21% | 14% |
  | workers 4 | 22% | 73% | 4% |

  일의 양은 같은데, 스레드가 4개면 시간의 대부분이 readline 안에서 보인다.
- 해석 (가설, 아직 검증 안 함): zlib은 압축을 푸는 동안 GIL을 놓는다. 다 푼 뒤 Python으로 돌아오려면 GIL을 다시 잡아야 하는데, 그동안 다른 스레드가 json.loads로 GIL을 쥐고 있다. 그래서 다시 잡으려고 기다리는 시간이 readline 안에서 잡힌다. 늘어난 CPU 시간(+28%)은 GIL을 주고받는 비용이다.
- 원본 데이터: `w1_parse.txt`, `w4_parse.txt`, `w4_parse_idle.txt`, 불꽃 그래프 `w4_parse.svg`.

**다시 재 봤다**: 5절의 B 측정에서 thread 1 / 4를 다시 쟀다. 32.0 / 34.6초(0.92배)로 결론은 같다. 기준선 자체는 실행 묶음마다 15%쯤 흔들린다.


## 5. 해결 (B)와 다시 잰 숫자
> 막히면 Claude에게 힌트를 요청한다. 키트에는 답이 없다.

**B: 파일 단위 프로세스 병렬** (`--pool process`, 표준 라이브러리 ProcessPoolExecutor)
- 왜 이것인가
  - 프로세스마다 인터프리터와 GIL이 따로 있다. 그래서 json.loads가 진짜로 동시에 돈다.
  - raw는 그대로 둔다. 장점(D2)을 건드리지 않는다.
  - 원천 단위가 파일이라서 파일 하나를 작업 하나로 나누면 끝난다.
- 안 고른 것
  - 더 빠른 JSON 파서(orjson 등): 의존성이 하나 늘고, 코어 1개 한계는 그대로다. B와 같이 쓸 수는 있다.
  - 한 번만 파싱해서 열 형식으로 저장(D7 base 물리화): 재처리 횟수를 줄이는 방법이지 재처리 속도를 올리는 방법은 아니다. base 매핑을 바꾸면 결국 raw에서 다시 만들어야 하므로 B가 여전히 필요하다.

**B 예상 (실행 전)** PC는 Ryzen 7 7800X3D, 물리 코어 8개, 논리 코어 16개다.
- parse, process 4: 약 3.5배 (38.4 → 약 11초).
- parse, process 8: 약 5.5배. 물리 코어 8개를 다 쓰지만 파일 크기가 제각각이라 마지막 큰 파일을 기다린다.
- process 16에 파일 8개: process 8과 같다. gzip은 쪼갤 수 없어서 파일 수가 병렬 상한이다.
- 메모리: 프로세스당 약 30MB라서 8개면 약 250MB.
- 대가: 프로세스를 띄우는 비용(Windows는 spawn이라 프로세스마다 인터프리터를 새로 띄운다).

**B 측정** (2026-11-12, 같은 파일 8개, parse, 한 번에 이어서 실행)

| pool | workers | wall | cpu | 코어평균 | 코어최대 | RSS최대 | 기준 대비 |
|---|---|---|---|---|---|---|---|
| thread | 1 | 32.0s | 31.8s | 1.00 | 1.16 | 30MB | 기준 |
| thread | 4 | 34.6s | 42.1s | 1.22 | 1.58 | 31MB | 0.92배 |
| process | 1 | 30.9s | 32.1s | 1.04 | 1.31 | 58MB | 1.04배 |
| process | 2 | 15.9s | 32.4s | 2.03 | 2.46 | 87MB | 2.0배 |
| process | 4 | 9.7s | 34.2s | 3.51 | 4.39 | 146MB | 3.3배 |
| process | 8 | 6.6s | 38.7s | 5.84 | 8.10 | 261MB | **4.8배** |
| process | 16 | 6.9s | 39.9s | 5.77 | 8.06 | 263MB | 4.6배 |

- 기준선이 4절(38.4초)보다 빠르다(32.0초). 같은 날 같은 파일인데 실행 묶음마다 15%쯤 흔들린다. 그래서 비교는 한 번에 이어서 돌린 묶음 안에서만 한다.

| 질문 | 예상 | 실제 |
|---|---|---|
| process 4 | 3.5배 | 3.3배 |
| process 8 | 5.5배 | 4.8배 |
| process 16, 파일 8개 | 8개와 같다 | 같다 (4.6배) |
| 메모리, 8개 | 약 250MB | 261MB |

**예상 못 한 것: 동시에 돌면 파일 하나하나가 느려진다**

| 파일 | thread 1 | process 8 |
|---|---|---|
| 2025-01 | 5.6s | 6.3s |
| 2025-04 (가장 큼) | 5.7s | 6.5s |
| 2025-06 | 2.7s | 3.4s |
| 2025-11 (형식 변경 후) | 1.3s | 1.7s |

- CPU 총량이 31.8 → 38.7초로 22% 늘었다. 그런데 프로세스를 띄우는 비용 때문이 아니었다. process 1의 CPU는 32.1초로 거의 그대로다. 8개가 동시에 돌 때 파일마다 15~25% 느려진 것이다.
- 해석 (가설, 검증 안 함): 코어 1개만 바쁠 때는 부스트 클럭이 더 높다. 8개가 같이 돌면 클럭이 내려가고 L3 캐시와 메모리 대역폭을 나눠 쓴다.
- 전체 시간 6.6~6.8초는 가장 큰 파일(6.5초)에 프로세스를 띄우는 시간을 더한 값이다. **gzip 파일 하나는 쪼갤 수 없어서, 병렬의 최소 단위가 원천 파일 1개다.** 파일보다 프로세스가 많으면 놀고, 큰 파일 하나가 끝을 정한다.
- 덤: 2025-11 파일은 줄 수가 2025-06과 비슷한데 파싱은 절반 시간이다. 2025-10 payload 축소의 효과로 보인다(D13 측정에서 확인).


## 6. 지킨 장점 / 낸 대가
- 지킨 것: raw는 원본 json.gz 그대로다(D2). 한 줄도 바꾸지 않았다.
- 얻은 것: 다시 처리하는 속도가 4.8배다. 한 달 720개 기준 단일 스레드로 약 48분(파일당 평균 4.0초)이었는데, 프로세스 8개로 약 7~8분이다(파일당 CPU 4.9초 × 720 ÷ 8, 추정).
- 낸 것
  - 메모리가 30MB에서 261MB로 8.7배다.
  - CPU 총량이 22% 늘었다. 같은 일에 전기를 더 쓴다.
  - 병렬의 상한이 파일 수다. 한 시간 파일 하나만 다시 처리하면 하나도 안 빨라진다.
- 다음 문제 (안 풀었다): 큰 파일 하나가 끝을 정한다. 이걸 풀려면 원천 파일을 쪼갤 수 있는 형식으로 한 번 바꿔 둬야 한다. 그건 D7(base 물리화) 자리다.
- 다운로드(ingest.py)는 스레드 풀 그대로 둔다. 네트워크를 기다리는 동안은 GIL을 놓아서 G1의 문제가 생기지 않는다(이론상, 따로 재지 않았다).

## 서사 한 줄
**원천을 다시 받을 수 없을 때를 대비해** raw를 json.gz 그대로 뒀다 → 다시 처리해 보니 스레드를 4개로 늘려도 **0.92~0.99배**로 안 빨라지고 CPU만 **+28%** 더 썼다(GIL. py-spy로 보니 워커 시간의 68%가 대기였다) → **파일 단위 프로세스 병렬**로 바꿨다 → **4.8배** 빨라졌고 raw는 그대로다 → 대가로 메모리 **8.7배**를 썼고, gzip은 쪼갤 수 없어서 **병렬 상한이 파일 수**라는 다음 문제가 남았다.
