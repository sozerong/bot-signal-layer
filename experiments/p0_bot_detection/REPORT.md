# 봇 탐지 실험: GitHub vs 일반 웹

## 문제 정의

사용자 행동을 분석해야 하는 입장에서 봇은 노이즈다. 봇이 섞이면 실제 사용자가 무엇을 원하는지(조회, 전환, 인기)를 정확히 볼 수 없다. GitHub에서는 이 노이즈가 star 위조로 이어지고, 위조된 인기는 악성코드 유포 수단이 된다.

## 1. 봇의 정의

"이벤트를 만든 주체가 그 순간 사람의 의도가 아니라 프로그램인 것." 분석 관점에서는 사람의 의도를 반영하지 않는 이벤트 전부를 봇으로 본다.

두 축으로 나눴다. 탐지 난이도는 거의 전부 **선언 여부**가 정한다.

| | 스스로 봇이라고 밝힘 (선언) | 사람인 척함 (비선언) |
|---|---|---|
| **GitHub** | 이름이 `[bot]`으로 끝나는 GitHub App (dependabot 등) | 사람 계정으로 돌리는 스크립트, 가짜 star 계정 |
| **웹** | UA에 Googlebot 같은 이름을 달거나 robots.txt를 읽는 크롤러 | 브라우저 UA를 단 스크레이퍼, 헤드리스 브라우저, 클릭 봇 |
| 의도 | 대부분 무해 (색인, 의존성 업데이트) | 무해한 자동화부터 지표 조작, 악성코드 유포까지 |

## 2. GitHub 봇 탐지

**데이터**: GH Archive 2024-07-15 하루치 (StarScout 논문 기준 가짜 star가 정점이던 달). 이벤트 491만 건, 계정 66만 개.

### 결과

| 층 | 방법 | 결과 |
|---|---|---|
| L1 선언 봇 | login이 `[bot]`으로 끝남 | 계정 1,530개(0.2%)가 **전체 이벤트의 28.2%** |
| L2 비선언 자동화 | 하루 24시간 중 20시간 이상 활동 + 100건 이상 | 계정 428개가 이벤트의 9.7% |
| L3 가짜 star | 아래 v3 규칙 | 저장소 276개, **그날 전체 star의 12.1%** |

L2 규칙을 선언 봇(정답을 아는 집단)에 적용하면 55.8%만 잡혔다. 크론처럼 계속 도는 봇만 잡히고, PR이 열릴 때만 반응하는 봇은 사람처럼 쉬기 때문이다.

### L3 규칙의 변천 (같은 원본에 판정만 다시 계산)

| 버전 | 규칙 (공통: star 20개 이상, stargazer 절반 이상이 그날 star만 누른 계정) | 의심 저장소 | 문제 |
|---|---|---|---|
| v1 | 다른 저장소와 1시간 안에 같이 star한 계정이 10명 이상 | 133 | hello-algo, microsoft/graphrag 같은 **트렌딩 저장소 대량 오탐**. 트렌딩 페이지를 보고 여러 저장소를 몰아 누르는 실제 사용자도 같이 움직인다 |
| v2 | 위 숫자를 내 star 수로 나눈 **비율 0.5 이상** | 80 | 정상 트렌딩은 0.25 미만, 악성 캠페인은 0.5~1.0으로 갈림. 대신 하루 100개 넘게 star하는 계정 무리를 놓침 (쌍 폭발을 막으려고 계정당 50개 상한을 둔 탓) |
| v3 | v2 **또는** 가장 몰린 5분 구간에 star의 절반 이상 | 276 | 예: 65개 star가 35초 안에 들어온 저장소 |

v2의 구멍은 사후 검증에서 발견했다. 대조군 중 사라진 저장소를 열어 보니 `FL-Studio`, `CCleaner-Pro`, `DayZ-hck-2024` 같은 이름이 줄줄이 나왔다.

### 검증

정답 라벨이 없어서 **"2년 뒤 지금도 저장소가 살아 있나"**로 사후 검증했다. 가짜 star로 띄운 악성 저장소는 신고되면 삭제된다.

| 그룹 | 표본 | 사라짐 (404) |
|---|---|---|
| v3 의심 | 276 | **263 (95.3%)** |
| 대조군 (같은 날 star 20개 이상, 비의심) | 279 (rate limit으로 21개 미확인) | 10 (3.6%) |

- 살아남은 의심 저장소 13개 중 명백한 오탐은 star 20~30개짜리 정상 저장소 5개 정도다 (greatfrontend, bagisto 등). 작은 저장소는 비율 지표가 쉽게 흔들린다.
- 대조군에서 사라진 10개 중에는 허니팟 토큰, 솔라나 카피트레이딩 같은 이름이 있다. lockstep도 burst도 없이 시간을 두고 나눠 찍는 캠페인은 하루치로는 못 잡는다.

### 그 밖의 관찰

- "그날 star만 누른 계정"은 **계정 단위**로 보면 신호가 아니다. 전체 star의 79%가 이런 계정에서 나왔다. 하지만 **저장소 단위**로 90% 이상 몰려 있으면 강한 신호가 된다.
- 계정 나이 대신 actor_id를 썼다 (id는 가입 순서대로 증가한다). 신규 계정 비율은 캠페인마다 달랐다. 88% 신규인 캠페인도 있고, OBSERVER09처럼 13~20%만 신규인 캠페인도 있다. 신규 계정 여부만으로는 거를 수 없다.
- 탐지된 저장소 이름은 크랙 소프트웨어(Adobe, FL Studio, VPN Premium), 게임 핵, 크립토 자동봇, 다크넷 마켓 링크였다. 프로젝트 문제 정의(위조된 인기를 악성코드 유포에 쓴다)가 데이터에서 그대로 확인됐다.

## 3. 일반 웹 봇 탐지

**데이터**: Zenodo 3477932. 그리스 테살로니키 대학 도서관 검색엔진의 2018년 3월 nginx 로그, 요청 409만 건 (CC BY 4.0).
처음에는 이커머스 로그(Harvard Dataverse "Online Shopping Store")를 쓰려 했지만, 원본 로그 파일이 접근 제한이라 바꿨다. 상세 페이지 `/Record`를 상품 상세, 검색 `/Search`를 상품 검색으로 대응시켰다.

세션은 원 논문과 같은 정의(같은 IP와 UA, 30분 무활동이면 끊음)로 다시 만들었다. 결과는 67,417세션으로, 논문의 67,352와 거의 일치한다.

### 결과

| 층 | 방법 | 결과 |
|---|---|---|
| L1 선언 봇 | UA가 크롤러 목록 1,506개 패턴에 걸리거나 robots.txt를 요청 | 세션의 19.1%, 요청의 10.1% |
| L2 비선언 (규칙) | 브라우저 UA인데 요청 20개 이상이면서 CSS/JS, AJAX, 표지 이미지를 하나도 안 받음 | 69세션 |
| L2 비선언 (모델) | L1을 라벨로 행동 피처만 학습 (UA는 제외), 점수 0.8 이상 | 95세션 |

모델은 시간 순으로 나눠 평가했다 (앞 3주 학습, 마지막 1주 평가). AUC 0.987, precision 0.85, recall 0.95가 나왔다. 숫자는 좋지만 가장 중요한 피처가 referrer 없음(0.42)이었다. 위장하는 봇이 가장 쉽게 채울 수 있는 값이다.

### 지표 왜곡

| | 검색 세션 | 검색 후 상세 전환율 | 상세 조회수 |
|---|---|---|---|
| 전체 | 38,483 | 64.9% | 286,039 |
| 선언 봇 제외 | 37,234 | 64.8% | **123,679 (57% 감소)** |

봇은 검색을 하지 않고 상세 페이지를 바로 긁는다. 그래서 **조회수와 인기 지표는 절반 넘게 부풀고, 전환율 퍼널은 거의 그대로다.** 봇이 어떤 지표를 망가뜨리는지는 그 봇이 어떻게 움직이는지에 달려 있다.

### 비선언 봇 탐지: 확인하지 못함

- L2 후보를 열어 보니 대부분 Safari 검색 제안 기능(`com.apple.Safari.SearchHelper`)이나 Android 앱 HTTP 클라이언트(Dalvik)였다. 자동화이긴 하지만 크롤러 목록에 없을 뿐, 악의적인 봇은 아니다.
- 약한 검증 신호(낡은 브라우저 UA 비율, 선언 봇과 IP 공유)로 봐도 L2 후보(8.7%, 1.9%)와 사람 추정 세션(5.2%, 2.4%) 사이에 의미 있는 차이가 없었다.
- 반대로 가장 수상해 보인 세션들은 이랬다. 2015년식 Firefox 39~43 UA로 4시간 동안 분당 20건씩 요청했다. 그런데 IP가 155.207.x로, 대학 자체 대역으로 추정된다. 도서관 검색용 공용 PC라면 **한 세션이 여러 사람**이다.

## 4. 왜 웹이 더 어려운가: 구조적 차이

| | GitHub | 웹 로그 |
|---|---|---|
| 주체 식별 | 계정 id 고정, 가입 순서까지 알 수 있음 | IP+UA뿐. 둘 다 위조 가능하고 공유됨 (NAT, 공용 PC, 프록시). 세션은 30분이라는 추정으로 만든 것 |
| 이벤트 의미 | star, push처럼 의미가 정해진 행동 | HTTP 요청. 의도를 거꾸로 추론해야 함 |
| 정답 라벨 | 플랫폼의 사후 조치(삭제)가 늦게 도착하는 라벨 역할 | **라벨 자체가 자기 신고**(UA 목록, robots.txt). 그래서 모델은 "선언한 봇의 행동"만 배우고, 위장한 봇은 정의상 사람으로 라벨링됨 |
| 공격자 목표 | 숫자를 키우는 것 → 표적 저장소에 몰릴 수밖에 없음 → lockstep과 burst가 보임 | 스크레이퍼의 목표는 안 들키는 것 → 분산하고, 헤드리스 브라우저는 요청 단위로 보면 브라우저와 같음 |

핵심은 이것이다. **GitHub 가짜 star는 "보여지려는" 공격이라 표적에 몰리고, 그 몰림이 약점이 된다. 웹 스크레이퍼는 "안 보이려는" 공격이라 몰림이 없다.**
그래서 GitHub에서 얻은 방법은 이커머스의 가짜 클릭, 리뷰 조작, 랭킹 조작처럼 특정 상품을 띄우려는 봇에는 옮겨 갈 수 있다. 가격 스크레이핑 봇에는 옮겨 가지 않는다.

이커머스 플랫폼은 로그인 사용자 id(GitHub 쪽 장점)와 세션·디바이스 정보(웹 쪽 정보)를 둘 다 가진다. 두 방식을 합칠 수 있는 자리다.

## 5. 플랫폼 관점에서 남긴 것

- **원본은 지우지 않는다.** 판정은 `suspect_v1/v2/v3` 컬럼으로 붙였다. 규칙이 세 번 바뀌는 동안 재수집은 한 번도 없었고, 의심 star 비중은 9.8% → 5.5% → 12.1%로 바뀌었다.
- 규칙을 바꾼 계기는 매번 **사후 검증**이었다 (v1은 오탐, v2는 미탐). 규칙이 계속 바뀐다는 사실이 스트리밍 앞단에서 지우지 않고 플랫폼에서 판정하는 이유다.

## 6. 한계와 다음 단계

- 하루치만 봤다. 나눠 찍는 캠페인을 잡으려면 기간을 늘리고 계정별 이력을 누적해야 한다 (StarScout는 5년치를 씀).
- lockstep의 계정당 star 50개 상한은 계산량 때문에 둔 것이다. 기간을 늘리면 이 쌍 계산이 Spark 셔플 병목을 직접 다뤄 볼 지점이 된다.
- 웹 쪽은 비선언 봇의 정답이 없다. 다음에 시도할 방법은 둘이다. 하나는 정답을 직접 만드는 것이다. 내 사이트에 헤드리스 브라우저와 스크레이퍼를 돌려 라벨이 있는 봇 트래픽을 섞는다. 다른 하나는 HTTP 로그 밖의 신호(JS 실행 흔적, 마우스 이벤트)가 있는 데이터를 구하는 것이다.

## 실행 방법

```bash
pip install duckdb scikit-learn
# GitHub
for h in $(seq 0 23); do curl -sO https://data.gharchive.org/2024-07-15-$h.json.gz; done   # 약 3GB
python gh/01_ingest.py <gharchive_dir> data/gh_events.parquet
python gh/02_detect.py data/gh_events.parquet results
python gh/03_validate_exists.py results/gh_validation_sample.csv results/gh_validation_result.csv  # 429가 나면 재실행 (실패분만 다시 확인)
# 웹
curl -L -o public_v2.json https://zenodo.org/api/records/3477932/files/public_v2.json/content   # 3.2GB
curl -L -o crawler-user-agents.json https://raw.githubusercontent.com/monperrus/crawler-user-agents/master/crawler-user-agents.json
python web/01_ingest.py public_v2.json data/web_requests.parquet
python web/02_detect.py data/web_requests.parquet crawler-user-agents.json results
```
